# SOLUTION — Exercise 02: Point-in-Time Correctness

> Per-exercise solution. The cross-exercise rationale lives in
> [`../SOLUTION.md`](../SOLUTION.md); this file factors the Ex-02
> section into a self-contained reference for graders.

## 1. Solution overview

Ex-02 is the exercise the module calls its **most consequential**
(see [`../SOLUTION.md`](../SOLUTION.md) §Ex-02). It teaches one
discipline: when assembling a training set, each row's feature
values must be the values that were observable **as of that row's
label timestamp**, not whatever the latest feature value happens
to be at the time the training job runs.

The failure mode is quiet. Training looks accurate, offline
evaluation looks excellent, the model deploys, production
performance is noticeably worse than offline, and the gap
survives for weeks because the artifact that caused it — the
training set — was generated by a one-shot job and discarded.

The reference answer is a side-by-side:

1. A naive `JOIN` that leaks future information.
2. A point-in-time (PIT) `JOIN` that does not.
3. Feast's `get_historical_features()`, which is the point-in-time
   `JOIN` exposed as a one-line API call over the feature
   definitions from [`../exercise-01/features.py`](../exercise-01/features.py).

Learners must demonstrate they can (a) name the bug, (b) write
the correct SQL, and (c) delegate the correct SQL to the feature
store rather than rolling it by hand in every pipeline.

## 2. Worked implementation

### 2.1 The naive join (wrong)

Given a `labels` table with `(user_id, label_ts, y)` and a
`user_clicks` feature source with `(user_id, event_ts, clicks_7d,
last_category)`, the naive query most learners write first is:

```sql
-- WRONG: leaks future data
SELECT
  l.user_id,
  l.label_ts,
  l.y,
  f.clicks_7d,
  f.last_category
FROM labels l
LEFT JOIN (
  SELECT user_id, clicks_7d, last_category
  FROM user_clicks
  WHERE (user_id, event_ts) IN (
    SELECT user_id, MAX(event_ts) FROM user_clicks GROUP BY user_id
  )
) f USING (user_id);
```

Every row of the training set is paired with the **latest**
feature row for that user — including feature observations that
happened *after* the label. A model trained on this learns to
use future information, so its offline score is inflated and its
production score collapses to something like the model it would
have been without the leakage.

### 2.2 The correct point-in-time join

The correct query selects, for each label row, the most recent
feature row whose `event_ts <= label_ts`, and further restricts
to feature rows inside the feature view's TTL (here, 7 days from
[`../exercise-01/features.py`](../exercise-01/features.py)):

```sql
-- RIGHT: value as of label_ts, bounded by TTL
SELECT
  l.user_id,
  l.label_ts,
  l.y,
  f.clicks_7d,
  f.last_category
FROM labels l
LEFT JOIN LATERAL (
  SELECT clicks_7d, last_category, event_ts
  FROM user_clicks f
  WHERE f.user_id = l.user_id
    AND f.event_ts <= l.label_ts
    AND f.event_ts >  l.label_ts - INTERVAL '7 days'
  ORDER BY f.event_ts DESC
  LIMIT 1
) f ON TRUE;
```

Three constraints, all required:

- `f.event_ts <= l.label_ts` — do not read the future.
- `f.event_ts > l.label_ts - INTERVAL '7 days'` — respect the
  feature view's `ttl=timedelta(days=7)` from
  [`../exercise-01/features.py`](../exercise-01/features.py);
  values older than TTL are considered stale and must not be
  served.
- Per-entity `ORDER BY event_ts DESC LIMIT 1` — pick the single
  most recent value, not an aggregate.

Any hand-rolled version of this join that drops one of the three
constraints is wrong. The second one (TTL) is the one graders see
dropped most often.

### 2.3 The Feast call (what learners should actually ship)

In production pipelines the hand-rolled SQL is a diagnostic, not
the shipped artifact. The shipped artifact is
`FeatureStore.get_historical_features`:

```python
# get_training_features.py
from feast import FeatureStore
import pandas as pd

fs = FeatureStore(repo_path="../exercise-01")  # same repo

entity_df = pd.read_parquet("data/labels.parquet")  # columns: user_id, event_timestamp, y
assert "event_timestamp" in entity_df.columns, (
    "Feast requires the label timestamp column to be named 'event_timestamp'."
)

training_df = fs.get_historical_features(
    entity_df=entity_df,
    features=[
        "user_clicks:clicks_7d",
        "user_clicks:last_category",
        "user_purchase:purchases_30d",
        "user_purchase:ltv",
    ],
).to_df()

training_df.to_parquet("data/training.parquet", index=False)
```

The entity DataFrame's `event_timestamp` column carries the label
timestamp. Feast walks every requested feature view, applies the
view's declared TTL, and performs the lateral-join equivalent
across all feature views in one call. This is the one-line API
change the module calls out in [`../SOLUTION.md`](../SOLUTION.md)
§Ex-02.

### 2.4 Decision rationale

- **Why delegate to Feast instead of hand-rolled SQL?** Every
  team that rolls its own PIT join eventually drops the TTL
  bound (quiet staleness) or the per-entity `LIMIT 1` (duplicate
  rows that silently reweight the training set). Writing the
  join once in the feature store and exposing it as an API means
  the bug is fixed for every pipeline rather than relitigated in
  each one. This matches the module's framing: feature stores
  are infrastructure for preventing train-serve skew, not an ORM.
- **Why the TTL belongs in the join.** A value that was 60 days
  old at label time is not the value the online store would have
  served at that moment — the online store would have returned a
  miss. Honoring TTL on the training side keeps the training
  distribution consistent with what serving returns, which is
  the whole discipline the module is built to enforce.
- **Why a side-by-side worked example.** The bug is invisible if
  you only look at the correct version. Graders look for the
  learner to produce both, run both, and show that the naive one
  yields higher offline metrics on the same split — that is the
  only durable way to internalize that offline-metric-up is not
  a success signal on its own.

## 3. Validation steps

A learner's submission is valid if all of the following hold:

1. **Both joins are present and runnable.** Naive and PIT, with
   identical label and feature inputs. A submission that only
   shows the correct version has not demonstrated it understands
   the bug.
2. **Row counts match between the two joins.** If the naive join
   returns more rows than the PIT join for the same entity set,
   the learner has introduced per-entity duplicates and should
   fix the `LIMIT 1` / `GROUP BY` before continuing.
3. **A metric gap is reported.** Train the same model on both
   training sets, evaluate on the same held-out window **whose
   labels post-date the training window**, and report the offline
   metric for each. The naive-join model should score higher on
   its own training distribution and lower on the held-out window
   than the PIT-join model; the direction of the gap is the
   evidence that leakage happened.
4. **TTL is respected.** For a random sample of training rows,
   verify that no joined feature row has
   `feature.event_ts <= label.event_ts - ttl`. A one-line
   assertion in the pipeline is sufficient.
5. **The Feast call replaces the SQL in the shipped pipeline.**
   The naive and correct SQL are kept as diagnostics; the
   production training-set generator calls
   `fs.get_historical_features`. Hand-rolled SQL in the shipped
   path is a failing submission even if it is temporarily
   correct.

## 4. Rubric / review checklist

| Dimension | Pass | Fail |
|---|---|---|
| Names the bug | Explicitly identifies feature leakage from future-dated feature rows | Describes PIT as "a join optimization" |
| Naive join present | Runnable and visibly wrong (drops the `<=` bound) | Only the correct version is shown |
| PIT join correctness | Uses `<=` **and** TTL **and** per-entity `LIMIT 1` | Any one of the three missing |
| TTL discipline | TTL comes from the FeatureView declaration, not a magic number pasted into SQL | Hard-coded interval unrelated to the feature definition |
| Delegation to Feast | Production path uses `fs.get_historical_features`; SQL kept only as diagnostic | SQL shipped as the production path |
| Metric-gap evidence | Side-by-side model evaluation shows the leakage-induced gap on a held-out window | No evaluation, or evaluation only on the training window |
| Entity-dataframe hygiene | `event_timestamp` column name used, no silent timezone coercion | Timestamp column mis-named or comparing naive vs aware timestamps |

A submission passes if every row is at Pass; any Fail row is sent
back regardless of how polished the rest is.

## 5. Common mistakes

Carried forward from
[`../SOLUTION.md`](../SOLUTION.md#common-mistakes-graders-see)
items 1–2, plus patterns specific to this exercise:

1. **Dropping the TTL bound.** The join compiles, the training set
   builds, and feature values that would have been online-store
   misses at label time silently appear in training. The model
   learns to depend on a value that will not be there at serving.
2. **Using `MAX(event_ts)` without a `<= label_ts` predicate.**
   This is the canonical "latest feature value" join; it is the
   exact failure the exercise is designed to catch.
3. **Per-entity duplicates.** A join that returns multiple
   feature rows per label row silently reweights the training
   set toward active users. Always `LIMIT 1` after ordering, or
   use `DISTINCT ON (user_id)` / window functions.
4. **Evaluating on the training window.** Measuring the leakage
   gap on data from the same time window the model trained on
   hides the leakage — the model has already seen the future.
   The held-out window must post-date the training window.
5. **Hand-rolling PIT SQL in each downstream pipeline.** Even if
   the first author gets it right, the second author copying it
   drops the TTL bound, and the leakage comes back. The join
   lives in the feature store exactly once.
6. **Mismatched timestamp column name.** Feast expects the entity
   DataFrame's label timestamp column to be named
   `event_timestamp`. A mis-named column throws late, inside the
   join, with a confusing message.
